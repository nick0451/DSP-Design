# 2. Q8 — CLOSED. Safeload located, with three caveats that change the loader design.

**Method: `pdftotext -layout`, "Software Safeload" section, Rev. C p.86. T1.**

**Table 53, Software Safeload Memory Address Defaults:**

    0x6000-0x6004  data_SafeLoad[0..4]   five data slots
    0x6005         address_SafeLoad      target address in parameter RAM
    0x6006         num_SafeLoad_Lower    count + TRIGGER, Page 1 lower memory
    0x6007         num_SafeLoad_Upper    count + TRIGGER, Page 2 upper memory

**The §5 contract's description — *"1-5 parameters per transaction, page-split addressing"* — is
CONFIRMED exactly.**

## ⚠ Caveat 1: these addresses are COMPILER-ASSIGNED, not architectural

> *"The exact parameter addresses are **not fixed**; therefore, the addresses must be obtained by
> reading the log file generated by the compiler… the compiler generates a file named
> **`compiler_output.log`** in the project folder… In this file, the addresses assigned to the
> software safeload parameters can be confirmed."*

**Table 53 is a table of DEFAULTS that match "in most cases".** Combined with the operator's Q3
decree — **there is no SigmaStudio project yet** — this means:

> **The loader must NOT hard-code `0x6000`–`0x6007`.** They are inputs, sourced from
> `compiler_output.log`, and they can move when the project is compiled. **This is precisely what
> makes the operator's "defined loader interface" necessary rather than tidy.**

## ⚠ Caveat 2 — W4, a FOURTH timing window, and the failure is silent corruption

> *"The safeload mechanism is software based and **executes once per audio frame**… A delay equal to
> or greater than the sampling period is required **between each safeload write**. At a sample rate
> of 48 kHz, the delay is equal to 20.83 µs. **Not observing this delay corrupts the downloaded
> data.**"*

*(The µ is lost by `pdftotext`; the extracted text reads "20.83 s". 1/48000 = 20.833 µs.)*

    W4  >= 20.83 us between consecutive safeload writes, at 48 kHz.  Bus: SPI0.
        Distinct from W1 (PLL lock), W2 (ADC bus-quiet), W3 (ADC reset-for-format).
        Four windows now, four causes, and NONE of them is the same delay.

**It is a per-write rate limit on a bus fast enough to violate it trivially** — an ESP32 SPI burst
will outrun 20.83 µs without effort — **and the penalty is corrupted parameters, not an error.**

## ⚠ Caveat 3: the trigger is the SECOND of two writes

> *"One of these values passed must always be a number between one and five inclusive, and the other
> value must be zero. **The second write triggers the safeload operation.**"*

**Both `num_SafeLoad_Lower` and `num_SafeLoad_Upper` are written every time — one with 1…5, the
other with 0 — and the ordering matters because the second write is the trigger.** Step 1 of the
vendor's own procedure is *"confirm that no safeload operation has been executed in the span of the
last audio sample"*, so **firmware must track the last safeload timestamp**, not merely rate-limit.

# 3. FW-018 — the ADAU1466's slave port DEFAULTS TO I2C. This is in neither §7.2 nor the contract.

**Method: `pdftotext -layout`, "Slave Control Ports", Rev. C p.35. T1, verbatim:**

> *"**The slave communications port defaults to I2C mode**; however, it can be put into SPI mode by
> **toggling SS (SS/ADDR0), the slave select pin, from high to low three times**. The slave select
> pin must be held low for **at least one master clock period** (that is, one period of the clock on
> the XTALIN_MCLK input pin)."*

**And the System Initialization Sequence, p.26, step 4:**

> *"If SPI slave control mode is desired, toggle the SS/ADDR0 pin three times… When the SS/ADDR0
> line rises for the third time, the slave control port is then in SPI mode."*

**`REQUIREMENTS.md` §5 puts the ESP32 on SPI0 to the DSP slave port. §7.2 step 3 is *"ESP32 releases
DSP reset"* and 3a goes straight to the PLL writes. Neither step mentions the toggle.**

> **Without it the port is in I2C mode, every SPI write is ignored, and step 3a's PLL configuration
> goes nowhere.**

**And here is the part that makes it nasty:** §7.2 3a already warns that a firmware that skips the
PLL-lock poll *"presents as an SPI wiring fault"*. **This produces the identical symptom from a
different cause.** Two distinct defects, one presentation — and a bench engineer who reads §7.2's
warning will chase the PLL explanation for a fault that is actually the missing toggle.

**Firmware can do it, and I confirmed the wiring rather than assuming:**

    U1  ~{SS}/ADDR0 (pin 33) -> SPI_DSP_SS_N -> U20 (ESP32-S3) IO16   [GPIO16]

**GPIO16 is an ordinary GPIO before the SPI peripheral claims it**, so the three toggles are a
bit-bang before SPI init. **One MCLK period at 24.576 MHz is 40.7 ns** — no timing difficulty; it
just has to happen. **`BOOT.md` now has it as step 2b.**

# 4. FW-019 — a correction to a claim this project has carried since F20

**Same paragraph, p.35:**

> *"**Only the PLL configuration registers (0xF000 to 0xF004) are accessible before the PLL locks.**
> For this reason, always write to the PLL registers first after the chip powers up. After the PLL
> locks, the remaining registers and the RAM become accessible."*

**`BRINGUP.md` §1.1 and the §5 contract both state that the slave ports are *inactive and every

> **The accurate statement: the PLL registers `0xF000`–`0xF004` ARE accessible before lock;
> everything else is not.** F20's *behaviour* and its whole point — poll `PLL_LOCK` before any
> program write — are untouched. **Only the mechanism was overstated.**

**Yours to correct or not; I am not editing `BRINGUP.md`.** Flagging because that sentence is
written for a bench engineer at 2 a.m., and *"every write fails"* invites exactly the wrong

# 5. Two more vendor init steps neither document carries

**From the System Initialization Sequence (p.26) and Table 19:**

- **`0xF890` `SOFT_RESET`** — Table 19's first entries are *enter soft reset* (`0x0000`) then *exit

**Calibration, because I do not want to hand you a false alarm:** a fixed pass over the netlist finds

**But `SELFBOOT` differs from the others in kind, which is why it gets named separately:**

> **It is a MODE INPUT whose floating state changes boot behaviour.** Init step 3: *"If the SELFBOOT

**A spare BCLK with no header is a to-do. A floating mode pin is a behaviour.** Worth a pull-down
